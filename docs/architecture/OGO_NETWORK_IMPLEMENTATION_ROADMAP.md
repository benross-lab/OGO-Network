## 1. Purpose

This document is the incremental implementation plan: Phase 1 Architecture, Phase 2 Local prototype, Phase 3 Multi-validator testnet, Phase 4 Public testnet preparation, Phase 5 Mainnet readiness. It maps each phase to the plan's milestones (M0 to M8), states the deliverables and acceptance criteria for each phase, and names the security, legal, and genesis review gates that must not be skipped. No phase is claimed as complete on the basis of code written; a phase is complete when its acceptance criteria pass with recorded evidence.

Phase mapping to the plan's milestones: Phase 1 covers M0 (Architecture and Decisions). Phase 2 covers M1 (Localnet Proof), M2 (Monetary Prototype), and M3 (Validator Prototype). Phase 3 covers M4 (Wallet Prototype), M5 (App Integration), and M6 (RPC and Indexer). Phase 4 covers M7 (Testnet). Phase 5 covers M8 (Mainnet Readiness). The plan's Phase 0 (Protocol specification) is Phase 1 in this roadmap; the numbering differs, the work does not.

Framework status: Cosmos SDK plus CometBFT is the recommended framework candidate, not a finalized selection. It is the stack the proof of concept runs on, continuing from the verified Milestone B scaffold, because that is where the verified monetary work exists. Final framework selection requires the proof of concept (plan section 2.6) to pass. If a MUST criterion fails for a reason structural to the SDK or CometBFT, the next step is a time-boxed Substrate spike that re-implements x/monetary as a FRAME pallet and re-runs the bypass suite, not a full rewrite. That spike is not authorized by this roadmap. No language in this roadmap that names the Cosmos dependency matrix, the SDK modules, or the Milestone B scaffold is a final framework selection; it is the candidate stack under evaluation.

## 3. Phase 2: Local prototype

This is the immediate focus after Phase 1. Work items, in order:

1. **Initialize a separate OGO Network repository.** Create the OGO-Network repository (explicit approval required for the creation itself) with the layout in `OGO_NETWORK_ARCHITECTURE.md` section 4. The repository starts from the Milestone B scaffold, not from zero. The scaffold lives in staging at `ogo-network-milestone-b/chain/`; it is moved into the repository with its history and its test results intact, not rewritten.
2. **Local dev chain.** A local development chain that produces blocks, with the verified dependency matrix for the candidate stack (Go 1.25.7, SDK v0.53.6 required with v0.53.4 effective, CometBFT v0.38.23, wasmd v0.60.9, ibc-go v10.7.0, Cosmovisor v1.7.3). This matrix is the proof-of-concept candidate stack, not a finalized framework selection. Reproducible build re-proven (clean-copy build, vet, tests, byte-identical hash under the canonical GOMODCACHE condition).
3. **Native denomination.** The `uogo` denom (proposed, 6 decimals) wired through x/bank, with supply queries, transfers, and burns working.
4. **Basic transfers.** Signed, sequence-checked transactions through x/auth, replacing the scaffold's unsigned JSON transactions. A transfer commits with the correct balances, and an invalid signature or a wrong sequence is rejected before execution.
5. **Deterministic monetary-engine interfaces.** x/monetary built to the common issuance interface (`OGO_MONETARY_ENGINE_SPEC.md` section 4), with the issued-by-epoch set, the amount-less `MintScheduled` entrypoint, and the every-block invariant. x/treasury and x/rewards built to their specifications.
6. **Configurable issuance models.** Both models (geometric and hybrid, with the optional gentle terminal taper) available in the simulator and in the engine, selected through genesis configuration, not by redesigning the engine. The simulator generates test vectors used as golden tests for x/monetary.
7. **Automated accounting tests.** The 11 supply invariants (`OGO_MONETARY_ENGINE_SPEC.md` section 10) as automated tests, plus the 54 Milestone B tests re-run on the wired chain, plus new tests for the wired keepers. The bypass suite (17 tests on the scaffold) re-run on the wired chain, with zero bypasses succeeding.
8. **Epoch migration.** The schedule migrated from block-based periods (scaffold) to epoch-based periods (x/epochs), with the StoreUpgrade tested, the mandatory depinject hook-fires test passing, and the halt and catch-up test (S4) passing. The hook-fires test is release-blocking for the monetary prototype and confirms five things, in order: (1) the epoch module initializes in the wired application, (2) the monetary hook is registered in the wired hook set, (3) the hook actually fires at an epoch transition, (4) exactly one scheduled issuance occurs for that epoch, (5) a duplicate hook execution cannot issue twice. Compilation alone is not an acceptable test. (See `OGO_CONSENSUS_AND_EPOCH_SPEC.md` section 13 and `OGO_NETWORK_ACCEPTANCE_CRITERIA.md` M2-5.)
9. **First proof (M1).** Three independent local validator nodes, genesis accounts, test OGO Coin transferred between wallets, and the same balances verified from all three nodes. All numbers TEST-ONLY. Validator count decided by Benross, 2026-11-06 (Phase 2 Execution Directive): THREE for the authorized local prototype. Correction note, 2026-11-06: the reconciliation pass had resolved this to 4 with BFT reasoning (3f+1; a 3-validator network tolerates zero faulty validators and halts if any one goes down). Benross's decision supersedes that resolution for the local prototype. The distinction to keep: 3 is the decided local-prototype execution requirement; 4 is the minimum operational set (Definition A, the smallest set tolerating one faulty validator, the target for the slashing and liveness test S5 on a later network); 50 or more is the decentralization target (Definition B) for a public network. The earlier figure of 3 in plan section 9.2 (M1) is therefore restored, and the plan text is corrected in v1.1. This resolution is about the M1 proof count only; it does not decide the launch validator minimum, which remains the open decision between Definition A (4 validators) and Definition B (at least 50 validators) in the decision register.
10. **Validator prototype (M3).** A 4-validator localnet (7 as the target) with staking, delegation, unbonding, slashing, remote signing (cosmos/kms), a Cosmovisor upgrade with a store migration, and a rollback of one validator after a failed upgrade.
11. **Separate four-validator framework-selection proof of concept (Option 1, decided by Benross 2026-11-06, executed 2026-11-06).** A separate, isolated 4-validator network (`ogo-network-poc-4validator/`, chain-id `ogo-poc-4val-1`), built from the same Milestone B scaffold and locked dependency matrix as the 3-validator prototype, which stays unchanged. It executed the applicable P1, S5, M2, and O1 criteria: S5 liveness demonstrated (voting power 10 per validator, total 40; blocks continued with val4 down, height 18 to 30 over 30 s; val4 restarted, caught up to height 31, all four nodes agreeing on app hash, balances, supply 1,000,002,710, issued 2,710); P1 partially executed (observed windows 149 s and 144 s, 100 percent of 159 block-time intervals within 1 to 10 s; the 24-hour duration remains open); M2 not executed (no Cosmovisor or upgrade-handler support in the scaffold); O1 partially executed (runbook written, start, stop, snapshot, restore executed; no sentry topology on a single machine). S5 jailing and slashing were not executed and not claimed (x/slashing not wired, blocker B6). Full report: `ogo-network-poc-4validator/ogo-network-poc-4validator-report.md`. Distinctions: 3 is the approved Phase 2 local prototype; 4 is the separate framework-selection fault-tolerance test; 50 or more is a proposed decentralization target, not an approved launch parameter. Disposition, decided by Benross 2026-11-06: the fault-tolerance result is ACCEPTED as established, not provisional. S5 liveness passed; jailing, slashing, and unjailed rejoin remain open for Milestone C. P1 open until the full 24-hour observation is completed. M2 open and framework-selection blocking until a genuine Cosmovisor upgrade and state migration are executed successfully. O1 start, stop, snapshot, and restore accepted as partial evidence; sentry topology, independent validator operation, and the upgrade procedure remain open. Overall framework selection remains open pending the remaining mandatory criteria.

Acceptance criteria: the proof-of-concept criteria pass (P1 to P5, S1 to S8, M1 to M5, O1, O2, O5). Correction note, 2026-11-06: O3 (IBC smoke test) and O4 (Keplr or Leap wallet smoke test) are REMOVED from the framework-selection criteria by Benross's decision (Phase 2 Execution Directive). Keplr and IBC are separated from framework-selection tests and are not prerequisites for the initial monetary prototype unless a specific technical dependency demonstrates necessity. They are evaluated separately when that dependency arises. The proof of concept therefore has 21 MUST criteria (P1 to P5, S1 to S8, M1 to M5, O1, O2, O5), not 23; the earlier figure of 23 included O3 and O4. In particular: multi-validator block production for 24 hours (P1); 200 TPS simple transfers and 50 TPS mixed load (P2, P3); p95 finality under 6 seconds (P4); signature verification proven (S1); the bypass suite re-run with zero successes (S2); exact once-only epoch issuance (S3); 30-minute halt catch-up with no lump, no skip, and no double mint (S4); slashing and liveness (S5); double-sign protection (S6); live wasm sandbox test (S7); remote signer (S8); reproducible build re-proven (M1); Cosmovisor upgrade with identical balances and supply before and after (M2); bypass suite re-run after upgrade (M3); dependency upgrade dry run to SDK 0.55 with a written effort estimate (M4); rollback (M5); multi-validator operation with a runbook (O1); monitoring and alerting demonstrated (O2); snapshot recovery (O5).

Security gate (Phase 2): the monetary bypass surface is re-tested on the wired chain, and the governance security boundary (five layers) is implemented and tested. The gate is not passed until S2, S3, S4, and M3 pass.

Capability checks versus prototype dependencies (reconciliation, 2026-11-06): the proof-of-concept criteria above are framework-selection gates, and each has one owning milestone, so a failure blocks exactly its owner plus framework selection, and no milestone is blocked by a criterion it does not own. (a) CosmWasm: criteria S7 (live wasm sandbox test) and P3 (mixed load including one CosmWasm contract call per block) are capability checks. They verify the candidate stack CAN execute CosmWasm safely, so framework selection can rely on that capability. They do not make CosmWasm a dependency of the first monetary prototype: M2 acceptance (S2, S3, S4 and the 11 supply invariants) must pass with CosmWasm disabled or unused by the monetary code, and the monetary prototype must not depend on any contract. The adoption decision is separate and later: after M3, CosmWasm is evaluated in staging against the eight criteria in plan section 9.4, and only if they pass is it enabled for the testnet (M7) with a documented contract review process. A failed S7 blocks framework selection until fixed or the framework is re-evaluated; a failed post-M3 adoption evaluation blocks CosmWasm adoption, not M0 to M3. (b) Keplr and IBC: criteria O4 (Keplr or Leap wallet smoke test) and O3 (live IBC smoke test to a second local chain) are REMOVED from framework-selection gates by Benross's decision, 2026-11-06 (Phase 2 Execution Directive). They are separated from framework-selection tests and are not prerequisites for the initial monetary prototype unless a specific technical dependency demonstrates necessity. They are evaluated separately when that dependency arises: the wallet product is built in M4, and live IBC to real external chains is later work (M7 testnet onward). An O4 or O3 evaluation, when it happens, is recorded with its result; it does not move wallet development earlier than M4 and does not block M0 to M3. (c) Per-milestone ownership: M1 owns the 3-validator localnet proof (blocks produced, transfer commits, identical balances from all three nodes, exact total supply); M2 owns S2, S3, S4 and the 11 supply invariants; M3 owns P1, S5, S6, S8, M2, M3, M5; the remaining criteria (P2, P3, P4, P5, S1, S7, M1, M4, O1, O2, O5) are framework-selection criteria exercised on the proof-of-concept localnet, and their results are recorded once and referenced by the milestones, not re-gated per milestone. Note: P1, S5, M2, and O1 are specified for a 4-validator network (S5 takes 1 of 4 offline and requires continued production). The M1 localnet proof runs 3 validators by Benross's decision. DECIDED by Benross, 2026-11-06 (Option 1): the proof-of-concept run uses a separate 4-validator network, in addition to the unchanged 3-validator local prototype; S5 is NOT redefined for a 3-validator network as a halt-and-resume demonstration. The separate 4-validator proof of concept ran on 2026-11-06; see item 11 below and `OGO_NETWORK_ACCEPTANCE_CRITERIA.md` section 3.6.

## 4. Phase 3: Multi-validator testnet

Work items:

1. **Wallet prototype (M4).** Software wallet with the abstract signing seam, mnemonic creation and recovery, Argon2id local storage, platform keystore, DIRECT and Amino JSON signing, send, receive, balance verification from chain state, history from the indexer, and off-chain agent authorization with immediate revocation. Keplr integration, or a documented blocker.
2. **App integration (M5).** Economy dashboard with three separate sections (Coins, Credits, native OGO Coin), wallet linking with signature verification, payment requests, agent payment permissions, developer payment APIs, and marketplace settlement gated on verified on-chain payment. The Worker must-never list is tested.
3. **RPC and indexer (M6).** Public RPC and LCD endpoints, an indexer, and the explorer. Indexer reconciliation (gate G9) passes. The explorer is usable without an OGO account.
4. **Multi-validator testnet.** A private multi-validator testnet (validators operated by OGO Systems and invited operators under a testnet agreement), with the full proof-of-concept criteria re-run, a governance upgrade executed, and an incident handled from the runbook.

Acceptance criteria: the wallet verification checklist (`OGO_NATIVE_WALLET_SPEC.md` section 17) passes in full; an end-to-end payment request flow is verified on the localnet (request, sign, commit, verify, mark paid); a duplicate webhook or duplicate request cannot fulfil twice; the indexer matches the chain exactly; the explorer displays balances and history matching the chain.

Security gate (Phase 3): wallet recovery (G7) and indexer reconciliation (G9) pass. The Worker must-never list is tested with no violation. No seed or private key is transmitted to any server, verified by inspecting network traffic and logs.

## 5. Phase 4: Public testnet preparation

Work items:

1. **Public testnet.** A public testnet with independent validators (not operated by OGO Systems), a faucet, documented genesis, and a testnet runbook. Validators join by bonding testnet tokens (TEST-ONLY, no real value) and meeting the onboarding requirements. The set is open.
2. **Governance on testnet.** A governance proposal is submitted, voted on, passed, and executed (a non-monetary parameter change). An expedited proposal path is evaluated, not assumed.
3. **Incident response.** An incident (a validator outage, or a halt) is handled using the runbook, and the handling is recorded. The halt and catch-up rule is exercised on the testnet, not just on the localnet.
4. **CosmWasm evaluation (adoption decision, not a capability re-check).** The eight CosmWasm evaluation criteria (`ogo-network-native-coin-architecture-implementation-plan-v1.0.md` section 9.4) are tested in staging. This is the adoption evaluation, distinct from the proof-of-concept capability check (S7 and P3), which already verified the stack can execute CosmWasm. If the eight criteria pass, CosmWasm is enabled for the testnet with a documented contract review process. If they fail, CosmWasm is deferred. No contract is deployed to a public network without a security review (audit 3).
5. **Documentation.** Validator guides, API specifications, and the operations runbook are published in OGO-Network-Docs and tested by an operator who did not write them.

Acceptance criteria: independent validators join and produce blocks; a governance upgrade is executed on the testnet; an incident is handled from the runbook; the testnet uses TEST-ONLY parameters, labelled so, with no real value; the documentation is usable by an independent operator.

Security gate (Phase 4): independent state validation (G1) is exercised: a third party obtains the source, builds the binary, runs the tests, and verifies the supply rules independently, with a written report. Operation during node outages (G10) is demonstrated on the testnet.

## 6. Phase 5: Mainnet readiness

Work items:

1. **Audits.** All five audits complete (monetary core; consensus, staking, and governance; contracts and IBC; wallet, keys, and RPC; build and supply chain), with written reports and a findings register. No unresolved critical or high findings.
2. **Legal review gate.** The legal analysis (securities, money transmission, tax, international distribution, exchange admission) is commissioned in writing and received. This is the longest-lead item and must be commissioned early, not left to Phase 5. If it has not been commissioned by Phase 4, Phase 5 cannot start.
3. **Genesis review gate.** Genesis parameters are approved by Benross in writing: max supply (derived as M = G + S_actual), genesis supply, issuance model and parameters, period length, split, fee policy, treasury spend level and rule, emergency reserve floor, validator minimum, governance thresholds, network name and chain id, denomination and decimals, bech32 prefix and derivation path. Each parameter is reviewed against the decision register, and any parameter without an approval is a blocker.
4. **Operations readiness.** Runbooks, monitoring, alerting, snapshots, and a rollback procedure are documented and tested. OGO-operated validators, sentry nodes, remote signing, and monitoring are in place. An incident response exercise is completed.
5. **Launch decision.** Benross approves the launch in writing, separately from approving readiness. M8 is readiness, not a launch.

Acceptance criteria: all testing gates G1 to G11 pass; audits have no unresolved critical or high findings; the legal analysis is on file; Benross approves the genesis parameters and the launch in writing.

Security gate (Phase 5): all gates G1 to G11 pass, and the findings register has no unresolved critical or high findings. Legal gate: the legal analysis is received and on file. Genesis gate: every genesis parameter is approved in writing. None of these gates may be skipped. A phase that skips a gate is not complete, and the next phase does not start.

## 7. Gates that must not be skipped

## 8. What the roadmap does not do

The roadmap does not select a monetary model or any monetary parameter. It does not approve a repository creation, a commit, a push, a publication, a deployment, a testnet, a mainnet, spending, or token issuance. Each of those needs a separate, explicit approval from Benross at the time it is requested. The roadmap does not set dates: no phase has a calendar date in this document, because dates depend on approvals, on audit scheduling, and on the legal analysis, none of which are controlled by the roadmap.
