# OGO Network Security Model

Status: Technical specification. Planning only. No audits commissioned, no production system to audit, no production change authorized.
Date: 2026-11-06
Companion document: `ogo-network-native-coin-architecture-implementation-plan-v1.0.md` (section 10)
Architecture direction: CONFIRMED AND LOCKED, Option B. OGO Network is an independent Layer 1 blockchain with native OGO Coin.

## 1. Purpose

This document states the threat model and the testing gates for OGO Network. It covers compromised validators, malicious governance proposals, private-key theft, RPC manipulation, network partitioning, and software supply-chain attacks, and it defines the testing gates: independent state validation, invalid signature and double-spend rejection, supply-cap enforcement, deterministic arithmetic, validator failure handling, upgrade safety, wallet recovery, treasury bypass resistance, indexer reconciliation, operation during node outages, and audits.

## 2. Security assumptions

- The chain is secure if more than two thirds of voting power is honest. If more than one third is malicious or offline, the chain halts. If more than two thirds is malicious, the chain can finalise arbitrary blocks. This is the CometBFT assumption, and it cannot be improved by application code.
- The monetary rules are secure if the code enforces them and the code cannot be changed without a visible upgrade. A hard fork can replace the code. The protection is transparency and independent operators, not a claim that a hard fork is impossible.
- A user's coins are secure if the user's keys are secure. There is no recovery for a lost mnemonic and no reversal for a stolen key. The wallet can only make theft harder and limit the damage.
- A public RPC endpoint is not trusted. Balances and transaction statuses are verified against at least two independent sources, or one source plus the indexer, and a discrepancy is flagged.

## 3. Threat model: nine threats

Each threat lists the attack path, the impact, the mitigations (design and operations), and the residual risk. Residual risk is stated honestly: no threat is claimed as eliminated.

### Threat 1: Single validator key compromise

Attack path: an attacker obtains a validator's consensus private key (through a host compromise, a backup leak, or an insider) and uses it to sign conflicting blocks or to impersonate the validator. Impact: the validator can be slashed for equivocation, its delegators lose stake, and if the compromised key is used to sign a malicious fork, the chain can halt or split. Likelihood drivers: plaintext keys on the validator host (the scaffold's localnet keys are plaintext, which is why they are localnet only), weak host security, and unencrypted backups. Mitigations: remote signing through cosmos/kms, with the consensus key never present as a plaintext file on the validator host (proof-of-concept criterion S8); hardware security module or cloud KMS for key storage; no key backups in plaintext; key rotation through the in-place rotation path (0.55 family) or unbond and re-bond (0.53 matrix); monitoring for unexpected signing behaviour. Residual risk: medium. A compromised remote signer is still a compromise, and the mitigation is detection speed, not prevention.

### Threat 2: Validator cartel

Attack path: a group of validators controlling more than one third of voting power colludes to halt the chain, censor transactions, or extract value; a group controlling more than two thirds can finalise arbitrary blocks. Impact: the chain halts, transactions are censored, or the ledger is rewritten. This is the single largest residual risk, and it is high at launch, because a new chain has few validators and stake is concentrated. Likelihood drivers: low validator count, concentrated stake, and a small number of entities operating multiple validators. Mitigations: the Definition B decentralization targets (at least 50 validators, Nakamoto coefficient at least 10, top 10 under 33 percent, no country or provider over 33 percent); a mechanism for a flat stake distribution, still to be named; transparent validator identities and voting power, visible in the explorer; a minimum validator set that grows with the network; and governance that can reduce a cartel's power only if the cartel does not already control governance. Residual risk: high at launch, decreasing only as the validator set grows and stake disperses. No framework choice and no code change eliminates this risk. It is a distribution problem, not a software problem, and it must be stated as such to Benross.

### Threat 3: Malicious governance proposal

Attack path: an attacker submits a governance proposal that changes a parameter, approves a treasury spend, or executes an upgrade that weakens a monetary guard, and the proposal passes because turnout is low, because the attacker controls enough stake, or because voters do not understand what the proposal does. Impact: the schedule is changed, the cap is raised, treasury funds are drained, or a backdoor is introduced through an upgrade. Mitigations: the governance security boundary in section 5 (parameter separation, upgrade-handler denylist, amount-less mint entrypoint, every-block invariant, public schedule queryability); voting thresholds, deposit, and quorum set before genesis (TBD); a timelock between a proposal passing and its execution, so the community can react; and a requirement that any proposal touching monetary state is rejected in code, not just by convention. Residual risk: medium. The denylist and the invariant are code, but a hard fork can still replace the code. The protection is transparency and independent operators, not a guarantee.

### Threat 4: User wallet key theft

Attack path: an attacker obtains a user's mnemonic or private key (through phishing, malware, a compromised wallet, or a backup leak) and drains the wallet. Impact: the user loses their coins. There is no recovery, because the wallet is noncustodial and there is no password reset. Mitigations: the wallet security rules in `OGO_NATIVE_WALLET_SPEC.md` (Argon2id, platform keystore, no seed transmitted to any server); the signing prompt rules (the user sees the exact amount and recipient before signing); user education at wallet creation (the mnemonic is displayed once, with a plain warning that losing it means losing the coins); and the agent authorization limits, which bound what an agent can spend even if the agent is compromised. Residual risk: medium to high. Phishing and malware are the dominant loss vectors in practice, and no wallet design eliminates them. The wallet can only make theft harder and limit the damage.

### Threat 5: Validator key theft (operational keys)

Attack path: distinct from threat 1 (consensus key), this is theft of a validator's operator key, withdrawal key, or the keys used to manage the validator (unbonding, commission changes, governance votes). Impact: the attacker can unbond and withdraw the validator's stake, change its commission to 100 percent, or vote its stake in governance. Mitigations: operator keys held in a separate keystore from consensus keys, with multisig for high-value operations (unbonding, commission changes above a threshold); commission change limits (notice period and maximum change per period, TBD); and monitoring for unexpected operator transactions. Residual risk: medium. Multisig reduces the risk but adds operational complexity, and the multisig itself must be managed.

### Threat 6: Treasury key theft

Attack path: an attacker obtains control of the treasury module account or the keys that authorise treasury spending, and drains the treasury. Impact: the treasury is emptied, and the network loses its funding for development, grants, and validator support. Mitigations: the treasury is a module account, not a single key; spending goes through x/gov proposals within the R-F rule, so no single key can spend; the R-F rule bounds spending per period; the emergency reserve floor F prevents spending below the floor except through a separate emergency process; and all treasury transactions are public and visible in the explorer. Residual risk: low to medium. The module-account design removes the single-key failure, but a governance compromise (threat 3) can still approve a malicious treasury spend, which is why the R-F rule and the floor matter.

### Threat 7: RPC manipulation

Attack path: an attacker compromises or impersonates a public RPC or LCD endpoint, and returns false balances, false transaction statuses, or false supply figures to a wallet or to the OGO application. Impact: a user sees a wrong balance, a payment is marked as paid when it was not, or a marketplace settlement is triggered by a false verification. Mitigations: the wallet queries at least two independent RPC endpoints, or one RPC endpoint plus the indexer, and flags a discrepancy; the Worker verifies on-chain state against a public RPC endpoint and never trusts a client claim; the application labels cached values with the time they were last verified; and the explorer links to the chain for every value it displays. Residual risk: low to medium. The mitigations require the wallet and the application to actually implement multi-source verification, and a user who ignores a discrepancy warning is still at risk.

### Threat 8: Network partitioning

Attack path: a network partition (a cloud outage, a BGP hijack, a targeted denial of service, or a geographic split) divides the validator set so that no side has more than two thirds of voting power. Impact: the chain halts until the partition heals. If a side has more than two thirds, it continues, and the other side must catch up when the partition heals, with no double mint and no skipped epoch (the halt and catch-up rule). Mitigations: validators distributed across countries, providers, and networks (the Definition B target of no country or provider over 33 percent); sentry nodes that obscure the validator's network location; and the halt and catch-up rule, tested in the proof of concept (S4). Residual risk: medium. A partition that lasts long enough to halt the chain is a liveness failure, not a safety failure, and the chain recovers when the partition heals, but the downtime is real and must be communicated to users.

### Threat 9: Software supply-chain attack

Attack path: a compromised dependency (a Go module, a CosmWasm library, a build tool, or a CI action) introduces malicious code into the chain binary, the wallet, or the explorer. Impact: the malicious code can mint, steal keys, or exfiltrate data, depending on where it lands. This is a high residual risk, because the chain depends on a large module graph (the Gaia matrix) and on upstream projects that have had vulnerabilities (CWA-2026-006 in CosmWasm, GHSA-c32p-wcqj-j677 in CometBFT). Mitigations: pinned dependencies with hashes (go.sum), verified against the Gaia reference hash; reproducible builds, re-proven after every dependency change (M1); a dependency audit before each upgrade, with a written record of what changed and why; minimal dependencies (no dependency is added without a reason); and the audit plan in section 7, which includes a build and supply-chain audit. Residual risk: high. A supply-chain compromise is the hardest threat to detect, because the malicious code is inside a trusted dependency. The mitigations are detection and recovery, not prevention.

## 4. Monetary bypass surface

The monetary bypass surface is the set of paths by which the fixed-supply and schedule-only mint rules could be circumvented. Milestone B tested 17 bypass attempts on the scaffold, all failing. The bypass surface must be re-tested on the wired chain (proof-of-concept criterion S2), because wiring the keepers adds new paths.

Paths, and the test for each:

- **Module accounts:** a module account (rewards pool, treasury, distribution, or a custom module account) must not be able to mint, or to receive funds that were not minted through the schedule. Test: attempt to mint from each module account; attempt to transfer from a module account an amount greater than its balance; both fail, state unchanged.
- **Governance upgrades:** a governance proposal must not be able to change max supply, the schedule, or the final issuance period, either directly (a parameter change) or indirectly (an upgrade that modifies monetary state). Test: submit a proposal to change each; each is rejected or has no effect, and the schedule query returns the original values. Test an upgrade handler that attempts to modify monetary state; the denylist gate rejects it.
- **Smart-contract interfaces:** a CosmWasm contract must not be able to mint, or to call a bank send above its balance, or to call an unknown method. Test: deploy a test contract that attempts each; all fail, state unchanged (S7). The binding surface is frozen at [BankSend, BankBurn, QueryBalance, QuerySupply].
- **Founder mint:** there is no founder allocation, no reserved allocation, and no founder mint path. Test: attempt to mint to a founder address, or to create a genesis account with a founder purpose label; both fail.
- **Off-schedule mint:** minting must happen only at the scheduled amount, only once per epoch, only through the epoch hook. Test: attempt to mint an off-schedule amount; attempt to mint twice in the same epoch; both fail, issued total unchanged.
- **IBC escrow and voucher double-counting:** a native token escrowed on one chain and represented as a voucher on another must not be counted as two independent units of economic supply. Test: transfer out, verify escrow equals transferred amount and voucher equals transferred amount, and global economic supply is unchanged; transfer back, verify escrow released exactly (O3).
- **Dust as a minting allowance:** dust (the difference between S_target and S_actual) must never be issued as a top-up, a rounding buffer, or a discretionary mint. Test: after all epochs, attempt to mint the dust amount; it fails, and the dust remains unissued.

## 5. Governance security boundary: five code layers

The governance security boundary is enforced in five code layers. Each layer is a separate defence, so a failure in one layer does not by itself compromise the monetary rules.

1. **Parameter separation:** monetary parameters (max supply, schedule, final issuance period, treasury rule) are stored in x/monetary and x/treasury state, not in a generic parameter store that x/gov can change. A governance proposal that targets a monetary parameter has no parameter to change, because the parameter is not in the store it can reach.
2. **Upgrade-handler denylist gate:** every upgrade handler contains a denylist that rejects any upgrade attempting to modify monetary state (max supply, schedule, issued-by-epoch set, treasury rule) outside the constitutional process. The denylist is checked before the migration runs, and a rejected upgrade does not apply any part of its migration. The denylist is tested by submitting an upgrade that attempts a monetary change and observing the rejection.
3. **Amount-less MintScheduled entrypoint:** the mint function takes no amount argument. It takes only the epoch number, and it mints exactly R_n for that epoch, as computed from the genesis-fixed schedule. There is no code path that mints an arbitrary amount, so a caller cannot request a larger mint even if it can call the function.
4. **Every-block invariant:** at every block, the chain checks the supply invariants (total supply equals genesis plus issued minus burned; total issued is less than or equal to total scheduled; total supply is less than or equal to max supply). If the invariant fails, the block is rejected or the chain halts, per the configured behaviour, and the failure is logged. The invariant is a separate module (x/monetary invariants), not inline in the mint code, so a bug in the mint code is caught by the invariant.
5. **Public schedule queryability:** the schedule, the issued-by-epoch set, total issued, total scheduled, dust, and max supply are all public queries. Anyone can verify the rules without trusting OGO Systems, and any deviation is visible in the explorer. Transparency is the last layer, and it is the one that catches a failure in the other four layers after the fact.

Hard-fork caveat, stated honestly: no chain can promise its community will never adopt different software. A hard fork that replaces the code can remove all five layers. The protection is transparent rules, independent operators, and a visible upgrade process, not a claim that a hard fork is impossible.

## 6. Testing gates G1 to G11

Each gate has a concrete pass evidence. A gate is not passed by a claim; it is passed by the evidence listed.

- **G1, independent state validation.** Pass evidence: a third party (not OGO Systems, not the team that built the chain) obtains the source, builds the binary, runs the tests, and verifies the supply rules independently, with a written report. The reproducible build (M1) is the prerequisite. The third party's report is filed, not just asserted.
- **G2, invalid signature and double-spend rejection.** Pass evidence: a transaction with an invalid signature is rejected before execution, with the reason logged; a transaction that spends the same funds twice (a double-spend attempt, or a replayed transaction with the same sequence) is rejected, with the reason logged; the chain state is unchanged after each attempt. This closes the Milestone B gap (unsigned transactions accepted).
- **G3, supply-cap enforcement.** Pass evidence: an attempt to mint above the cap fails; an attempt to mint after the final issuance period fails; total supply never exceeds M in any test run, including the halt and catch-up test (S4) and the upgrade test (M2).
- **G4, deterministic arithmetic.** Pass evidence: the same schedule, computed on two different machines and in two different orders, gives the same per-period amounts and the same total, exactly, in integer arithmetic; no floating point appears in any consensus-critical monetary code, verified by a code search; the test vectors in `OGO_MONETARY_ENGINE_SPEC.md` section 10 pass.
- **G5, validator failure handling.** Pass evidence: a validator taken offline for longer than the downtime window is jailed and slashed, the chain continues with the remaining validators, and the validator can unjail and rejoin (S5); a double-sign is punished (S6); a validator restored from a snapshot rejoins and catches up (O5).
- **G6, upgrade safety.** Pass evidence: a governance upgrade is executed through Cosmovisor, with a store migration, and balances and supply are identical before and after (M2); the bypass suite is re-run after the upgrade and still passes (M3); a failed upgrade on one validator is rolled back and the validator rejoins (M5); an upgrade attempting a monetary change is rejected by the denylist (section 4).
- **G7, wallet recovery.** Pass evidence: a wallet is recovered from a mnemonic on a different device, with the same address and balance; a wallet recovered from a mnemonic generated by Keplr recovers the same address and balance, and vice versa; no seed or private key is transmitted to any server, verified by inspecting network traffic and logs during wallet operations (`OGO_NATIVE_WALLET_SPEC.md` section 17, items 1, 6, and 9).
- **G8, treasury bypass resistance.** Pass evidence: an attempt to spend from the treasury above the R-F rule fails; an attempt to spend below the emergency reserve floor F fails (except through the documented emergency process); an attempt to mint directly into the treasury fails; a governance proposal to change the treasury rule outside the constitutional process is rejected or has no effect.
- **G9, indexer reconciliation.** Pass evidence: the indexer is run against the chain for a full test period, and every block, transaction, and balance in the indexer matches the chain exactly; any discrepancy is logged, investigated, and explained; if the indexer and the chain disagree, the chain wins, and the discrepancy is surfaced, not silently resolved.
- **G10, operation during node outages.** Pass evidence: the chain continues to produce blocks with 3 of 4 validators while one is offline; the application continues to display balances and history from a surviving RPC endpoint while one RPC endpoint is down; the wallet continues to work when OGO's website is unavailable, using only a public RPC endpoint and an independent wallet.
- **G11, audits.** Pass evidence: all five audits in section 7 are complete, with written reports; there are no unresolved critical or high findings; medium and low findings have owners and dates, or are documented as accepted risks with reasons.

## 7. Audit plan

Five audits, in order, each with a scope and an independence rule. Audits are ordered so the monetary core is audited first, because it is the hardest to fix after launch.

1. **Monetary core.** Scope: x/monetary, x/treasury, x/rewards, the issuance schedule, the cap enforcement, the issued-by-epoch set, the three-number accounting, the R-F rule, and the every-block invariant. Independence: the auditor has not written any of the monetary code.
2. **Consensus, staking, and governance.** Scope: the CometBFT configuration, x/staking, x/slashing, x/distribution, x/gov, x/upgrade, the upgrade-handler denylist, and the governance security boundary (five layers). Independence: the auditor has not written any of the consensus or governance code.
3. **Contracts and IBC.** Scope: the CosmWasm binding surface, the wasm VM configuration, the IBC escrow and voucher accounting, and any contract deployed on the testnet. Independence: the auditor has not written any of the contract or IBC code. This audit is required before any contract is deployed to a public network.
4. **Wallet, keys, and RPC.** Scope: the wallet (key generation, storage, signing, recovery), the agent authorization mechanism, the RPC and LCD endpoints, and the indexer. Independence: the auditor has not written any of the wallet or RPC code. This audit includes a network-traffic inspection to verify no seed or private key is transmitted.
5. **Build and supply chain.** Scope: the reproducible build, the dependency matrix, the CI pipeline, and the release process. Independence: the auditor has not configured the build or the CI. This audit verifies that the binary a user builds from source matches the binary that is released, and that no dependency has been substituted.

Findings register: a single register, with every finding from every audit, its severity (critical, high, medium, low), its status (open, fixed, accepted risk), its owner, and the date it was resolved or accepted. An accepted risk must have a written reason, and the reason must be approved by Benross. A critical or high finding is never an accepted risk before mainnet.

## 8. Residual risks

Ten residual risks, in order of severity. Each is a risk that remains after the mitigations in this document, and each must be communicated to Benross, not hidden.

1. Stake concentration and validator cartel (threat 2). High at launch. No code change eliminates it. It decreases only as the validator set grows and stake disperses.
2. Post-issuance fee funding. The fee transition has not happened on any comparison network. Under Low and Moderate fee scenarios, fee revenue never covers the minimum need. Under High, it does so only late. If fees never cover the need, the validator set shrinks or security degrades.
3. Software supply-chain compromise (threat 9). High. A compromised dependency is the hardest threat to detect. Mitigations are detection and recovery, not prevention.
4. Upgrade removing the checks. A hard fork or a malicious upgrade can remove the monetary guards. The denylist and the invariant are code, and code can be replaced. The protection is transparency and independent operators.
5. Governance capture. If an attacker controls enough stake, or if turnout is low, a malicious governance proposal can pass. The thresholds, deposit, and quorum are TBD, and they must be set to make capture expensive, not just possible.
6. Wallet key theft through phishing or malware (threat 4). The dominant loss vector in practice. The wallet can only make theft harder and limit the damage.
7. IBC and bridge accounting errors. The escrow and voucher accounting is tested at ledger level, but live IBC relaying is not yet wired, and any bridge is third-party trust. An accounting error in a bridge can create unbacked vouchers.
8. Epoch and timestamp edge cases. The epoch-based period architecture depends on the epochs module and on the halt and catch-up rule. An edge case in the epochs module, or a long halt, could cause a missed or double epoch. The proof of concept tests the 30-minute halt (S4), but longer halts and repeated halts are not yet tested.
9. Fee market mispricing for agents. A flat fee cannot serve both security and agent viability. If the fee is set too high, small agent payments become impractical. If it is set too low, validators are underpaid. The fee policy must state explicitly how agent transactions are priced, and it has not yet done so.
10. Legal and regulatory change. The legal analysis is not yet commissioned. A change in securities, money-transmission, or tax law could affect the network, the token, or the distribution. This is an external risk, not a code risk, and it must be tracked as one.
